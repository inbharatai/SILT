### 1. [CRITICAL] RollbackLayer.rollback path traversal injects arbitrary packets into the approved store, bypassing the gate — `src/asea/memory/store.py:179`

- **Class:** SAFE | **Category:** path-traversal | **Confidence:** high | **New vs existing audit:** yes
- **Status:** ✅ FIXED

**Summary:** The user-supplied rollback token is joined directly onto the snapshots directory with no confinement check, so a token containing '..' resolves outside snapshots and rollback() copies any *.json files it finds there into approved/, defeating the core containment property that only gate-promoted packets reach the receiver.

**Failure scenario:** An attacker (or anyone reaching the unauthenticated Studio API at POST /api/transfers/{job_id}/rollback, or the CLI `asea rollback --token ../..`) passes token='../..'. RollbackLayer.rollback computes source = <root>/m/snapshots/../..  = <root>, which exists, so the unknown-token guard does not fire. It then deletes every file in approved/ and copies every *.json under <root> into approved/. I verified this end-to-end: a crafted SkillPacket file planted in <root> appeared in store.list('approved') with human_approved_by='attacker' and arbitrary distilled_skill, having never passed evaluation or the gate. Because receivers read only from approved/, this packet is served at inference time. A high-risk-domain packet injected this way also bypasses the mandatory human-approval check (the gate never ran). The existing A5 adversarial test (test_a5_forged_rollback_token_raises) only asserts a NON-existent token raises; it does not cover an existing path reached via traversal.

**Fix:** In src/asea/memory/store.py, RollbackLayer.rollback, replace `source = self.store._dir(SNAPSHOTS) / token` with confinement:

    snapshots_dir = self.store._dir(SNAPSHOTS).resolve()
    source = (snapshots_dir / token).resolve()
    if source == snapshots_dir or not source.is_relative_to(snapshots_dir):
        raise RollbackError("rollback token escapes snapshots directory")
    if not source.exists():
        raise RollbackError("unknown snapshot token '{}'".format(token))

(Equivalently, validate the token against ^[A-Za-z0-9._-]+$ and reject any token containing "/" or ".." before joining.) Add regression tests in tests/test_adversarial.py asserting rollback(".."), rollback("../.."), rollback("../candidate"), and rollback("../rejected") all raise RollbackError, and that a crafted SkillPacket placed in <root> is NOT copied into approved/. Note is_relative_to requires Python 3.9+, which the project already targets.

### 2. [CRITICAL] Unauthenticated human-approval endpoint lets any caller promote high-risk medical/legal/finance packets — `src/asea/studio/server.py:279`

- **Class:** GATE/CORE | **Category:** authz-bypass | **Confidence:** high | **New vs existing audit:** yes
- **Status:** ⏸ HELD — GATE/CORE, held for sign-off (see §Held for sign-off)

**Summary:** POST /api/transfers/{job_id}/approve has no authentication, and the approver is a free-form string (min_length=3) that the gate trusts verbatim — gate.apply sets human_approved_by=approver and the human_approval check is only bool(human_approver), so any network caller can satisfy the 'named human approver' hard rule for HIGH-risk domains.

**Failure scenario:** A medical_triage transfer parks a packet in PENDING_HUMAN (HIGH-risk domain, cannot auto-promote per risk_report #3). Any unauthenticated caller POSTs {"packet_id": <id>, "approver": "abc"} to /api/transfers/{job_id}/approve. pipeline.approve_pending -> gate.apply(human_approver='abc') -> decide() check 'human_approval' evaluates bool('abc')=True -> packet stamped human_approved_by='abc', promoted, written to approved/ and shipped in /export bundles. The hard gate rule 'HIGH-risk domains require a named human approver' is satisfied by a 3-character string from an anonymous network request.

**Fix:** The suggested fix is correct and needs sign-off because it touches the gate's human_approval trust assumption (gate.py:289) and pipeline.approve_pending's approver parameter. Minimal remediation, in order of preference: (1) Add authentication middleware/dependency to the FastAPI app (e.g. API key or OAuth) on ALL mutating endpoints (/api/transfers, /api/transfers/{id}/approve, /rollback, /api/catalog) and pass the authenticated principal's identity as the approver instead of trusting request.approver — in approve(), replace approver=request.approver with the resolved principal. (2) As a defense-in-depth gate-side measure, gate.apply/gate.decide should accept an approver identity object/assertion verified upstream rather than a raw string, so the bool(human_approver) check cannot be satisfied by an anonymous string. (3) Until auth exists, bind the studio to a trusted network (localhost/loopback only) and document in risk_report.md that the human-approval gate assumes a trusted-network caller — this is an accepted-risk stopgap, not a fix. The honest minimal fix is (1)+(2); (3) is documentation of accepted risk if auth is deferred.

### 3. [HIGH] approve_pending does not catch the duplicate-content RollbackError — leaves packet in inconsistent state with no audit event — `src/asea/core/pipeline.py:368`

- **Class:** GATE/CORE | **Category:** missing-error-handling | **Confidence:** high | **New vs existing audit:** yes
- **Status:** ⏸ HELD — GATE/CORE, held for sign-off (see §Held for sign-off)

**Summary:** The human-approval path calls store.approve() without the try/except RollbackError that _finalize has, so a duplicate in approved/ raises uncaught, the packet is never re-persisted, and no human_decision audit event is recorded.

**Failure scenario:** Two PENDING_HUMAN packets A and B with identical distilled content for the same high-risk receiver (both parked pending human). Operator approves A via approve_pending: store.approve(A) succeeds (first of its content). Operator approves B via approve_pending: gate.apply marks B PROMOTED in memory, then store.approve(B) raises RollbackError('identical content already approved...') (store.py:90). The exception is not caught (pipeline.py:367-368), so audit.append('human_decision',...) at line 371 is never reached. On disk B remains PENDING_HUMAN in candidate/ (the in-memory PROMOTED was never persisted), approved/ is unchanged, and the hash chain has no record that the human decision was attempted. The packet is stuck pending and the operator only sees a stack trace. _finalize handles this exact case at lines 314-331; approve_pending is inconsistent.

**Fix:** In approve_pending (src/asea/core/pipeline.py:367-374), wrap self.store.approve(packet) in try/except RollbackError mirroring _finalize lines 314-331: on duplicate, set packet.rejection_reason = str(exc), then packet.promotion_status = PromotionStatus.REJECTED (reason before status, since validate_assignment requires a reason for REJECTED), call self.store.put_rejected(packet), and self.audit.append('duplicate_refused', actor=approver, packet_id=packet_id, detail={'reason': str(exc)}). Then return decision.to_dict() from that branch. Additionally, move the 'human_decision' audit.append (lines 371-374) so it is written on ALL branches (approved, rejected-gate, and duplicate-refused) — e.g. place a single self.audit.append('human_decision', actor=approver, packet_id=packet_id, detail=decision.to_dict()) in a position reached on every path (or append on each branch), guaranteeing the hash chain always records that a human decision was attempted. This edits only error-handling in core/pipeline.py; it does not touch gate.py, filters, promotion policy/thresholds, or strict_no_mock.
