SILT · Skill Interchange Layer with Trust-gating

Transfer the skill. Prove the gain. Adapt for the hardware you have.

A powerful model can still be missing one specialist capability. Another AI may already have it. SILT is built to transfer that narrow capability — not copy the teacher — verify what the learner can actually use, and explore hardware-aware adaptation for constrained deployment.

The SILT thesis

A model should not need to know everything from birth.

If the model you want to deploy is strong but lacks one measurable capability — a language, terminology set, task pattern, workflow, or other narrow skill — SILT asks whether that capability can be represented, transferred from a specialist system, and admitted only after evidence shows the learner improved.

TEACHER AI already has specialist skill X
↓
extract / represent the narrow capability
↓
held-out evidence + safety + regression checks
↓
LEARNER AI receives it only if the gate permits it
Transfer → Prove → Adapt

Three stages, one discipline: do not confuse a process completing with a capability improving.

01 · TRANSFER

Represent a narrow skill

The default L3 path creates an inspectable Skill Packet containing capability-specific material such as rules, mappings, glossary entries, exemplars, or structured instructions. The teacher's weights are not copied.

02 · PROVE

Evaluate on unseen cases

Extraction data and held-out evaluation are separated. SILT compares learner baseline vs. learner + candidate skill, checks regressions, provenance and safety, and returns PROMOTED, REJECTED, or PENDING_HUMAN.

03 · ADAPT

Fit the deployment constraint

Optional deep-apply can train a removable LoRA from already-approved packets and gate it again. SiltSpring extends the work toward quantized model states and per-skill certification for constrained hardware.

Architecture at a glance

The trust gate is the enforcement layer — not the whole purpose.

SILT separates how a capability is produced from whether the result is allowed into the learner. The core pipeline is shared; extraction, distillation, and task-success metrics are capability/modality-specific plugins.

DEFAULT · L3

Skill Packet mode

Approved skill material is used at inference time. No learner weights are changed. Candidate, approved, and rejected states remain physically separated.

OPTIONAL · L4

Deep-apply + Gate 2

Only Gate-1-approved packets become LoRA training material. The trained adapter is independently evaluated again. Adapters remain removable rather than being merged into base weights in the current design.

HARDWARE-AWARE

SiltSpring

Quantized states such as int8/int4/int2 can be evaluated per skill. A compressed state should not be treated as certified for a capability that no longer meets its evidence threshold.

Honest scope

What SILT claims — and what it does not.

What exists in the repository

  • Inspectable L3 Skill Packets and held-out A/B evaluation.
  • All-or-nothing promotion with regression, safety, provenance, rollback, and audit controls.
  • Mandatory named human approval for high-risk medical/legal/finance domains.
  • Optional removable LoRA deep-apply followed by an independent Gate 2.
  • SiltSpring work for quantized model-state adaptation/certification.
  • Local Studio, CLI, library interfaces, examples, tests, and recorded real-run findings.

What SILT does not claim

  • Universal arbitrary capability copying between any two models.
  • Complete transfer of a teacher model's knowledge or internal weights.
  • AGI or unrestricted autonomous self-improvement.
  • That any very large model can magically run on any tiny device.
  • A fabricated percentage of “knowledge transferred.” SILT reports measurable benchmark deltas and gate verdicts instead.
  • A universal safety guarantee: a gate can only measure what its tests and policies cover.
